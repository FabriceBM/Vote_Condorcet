# Vote_Condorcet: voting for a consensus with veto rights

A state-of-the-art note, with its code, on how a group should vote when:

- **H1, open agenda**: any voter may propose as many options as they wish;
- **H2, full ballots**: every voter judges *all* the options proposed;
- **H3, veto rights**: voters can veto options,

and the procedure must reach **the best compromise (R1)** without the group ever **getting stuck (R2)**.

**The PDFs of record** are in [`versions/v0.1_2026-10-21/`](versions/v0.1_2026-10-21/):
- the note;
- its two-page executive summary in English;
- its *synthèse* in French.

Audience: engineers, actuaries and readers with a quantitative background.

## The answer in one paragraph

Hard unanimity is rarely optimal: it breeds delay and status-quo bias, and in a large assembly it
deadlocks almost surely. The note recommends **Condorcet with a blocking quota, QVC(θ)**. Every voter
ranks all options on one ballot and marks the ones they find unacceptable. Options vetoed by at least a
share θ of the voters (one third by default) are excluded; if that excludes all of them, the least-vetoed
ones are kept. The Schulze winner among the remaining options is elected. Properties:

- it always decides, in one round;
- the status quo gets no default advantage;
- the winner is acceptable to more than two thirds of the voters whenever some option is;
- the majority decides among acceptable options;
- adding variants (clones) of an option changes nothing.

Its price is strategic blocking. The note quantifies that price and proposes safeguards: named, reasoned
vetoes, a quota of at least one quarter, and at most one revision round.

## Layout (same as Immo_S2)

| Folder | Content |
|---|---|
| `manuscript/` | The note's content, journal-agnostic: sections, preamble, bibliography, notes. Start with [`manuscript/README.md`](manuscript/README.md) |
| `summaries/` | Short documents derived from the note, by language then kind: `summaries/en/executive/`, `summaries/fr/executive/`. See [`summaries/README.md`](summaries/README.md) |
| `journals/working-paper/` | The LaTeX wrapper (layout only) |

| `outputs/tables/`, `outputs/figures/` | Generated by the scripts. Never edit by hand |

| `versions/` | PDFs of record |

## Build and reproduce

```bash
pip install -r simulations/python/requirements.txt
python3 simulations/python/voting.py --check        # rules against brute force and known results
python3 simulations/python/experiments.py --check   # Monte Carlo against known probabilities
python3 simulations/python/examples.py --check      # the worked examples of Section 6.4
python3 simulations/python/experiments.py           # all tables (a few minutes on 4 cores)
python3 simulations/python/examples.py
python3 simulations/python/figures.py
python3 simulations/python/key_numbers.py           # headline numbers for the summaries
python3 tools/concept_map.py                        # concept map (literature/concept-map/)
latexmk main.tex                                    # or: cd journals/working-paper && latexmk main.tex
(cd summaries/en/executive && latexmk main.tex)     # executive summary, English
(cd summaries/fr/executive && latexmk main.tex)     # synthèse, French
python3 tools/overleaf_zip.py --test                # overleaf.zip, tested as Overleaf compiles it
```

**On Overleaf**, upload `overleaf.zip` as a new project, or link the GitHub repository. Overleaf
compiles from the project root, whatever the main document, so every path works from there. Choose the
main document in Menu > Main document:
- `main.tex` for the note;
- `summaries/en/executive/main.tex` for the English summary;
- `summaries/fr/executive/main.tex` for the French synthèse.

Every election is drawn from its own seed, so the tables are identical from run to run.
